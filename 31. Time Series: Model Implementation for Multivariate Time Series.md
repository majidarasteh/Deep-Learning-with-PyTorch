# Model Implementation for Multivariate Time Series

The data-preparation procedure for multivariate time series is different from the univariate case because each time step contains multiple features. However, once the sliding windows and data loaders have been created, the overall model-training procedure remains largely unchanged.

In this section, we focus only on the changes required in the **model implementation**. The models considered are **FFNN, RNN, LSTM, GRU, Conv1D, and N-BEATS**.

The main difference is that the input now contains four features at each time step:

$$
X \in \mathbb{R}^{window\_{size} \times feature\_{size}}
$$

For our Bitcoin dataset:

$$
window\_size=60,\qquad feature\_size=4
$$

Therefore, each input sample has the shape:

```text
(60, 4)
```

and a batch has the shape:

```text
(batch_size, 60, 4)
```

The target remains the future `Price` values. For example, with:

```python
horizon = 3
```

the target has the shape:

```text
(batch_size, 3)
```

# 1. Parameters Shared by All Models

Many of the parameters used in the univariate models can remain unchanged.

For example:

```python
window_size = 60
feature_size = 4
hidden_size = 128
num_layers = 1
horizon = 3
```

The new parameter is:

```python
feature_size = 4
```

In the univariate case, we had only one feature:

```python
feature_size = 1
```

In the multivariate case, we have four:

```python
feature_size = 4
```

The meaning of the parameters is:

* `window_size`: number of previous time steps used as input.
* `feature_size`: number of variables observed at each time step.
* `hidden_size`: number of neurons in the hidden representation.
* `num_layers`: number of recurrent layers.
* `horizon`: number of future values predicted.

The following parameters can therefore remain unchanged initially:

```python
hidden_size = 128
num_layers = 1
horizon = 3
```

The important change is that `feature_size` must now represent the number of input variables.


# 2. FFNN: Difference from the Univariate FFNN

In the univariate case, an input window has:

$$
60 \times 1 = 60
$$

values.

Therefore, the first layer of the FFNN was:

```python
nn.Linear(window_size, hidden_size)
```

For multivariate data, every time step contains four features:

$$
60 \times 4 = 240
$$

Therefore, the FFNN must receive 240 values after flattening.

The input changes from:

```text
(batch_size, 60, 1)
```

to:

```text
(batch_size, 60, 4)
```

We flatten the last two dimensions:

```text
(batch_size, 60, 4)
            ↓
(batch_size, 240)
```

### Multivariate FFNN

```python
class FFNNModel(nn.Module):

    def __init__(
        self,
        window_size=60,
        feature_size=4,
        hidden_size=128,
        horizon=3
    ):
        super().__init__()

        self.model = nn.Sequential(

            nn.Linear(
                window_size * feature_size,
                hidden_size
            ),

            nn.ReLU(),

            nn.Linear(
                hidden_size,
                horizon
            )
        )

    def forward(self, x):

        # Flatten time and feature dimensions
        x = x.reshape(
            x.size(0),
            -1
        )

        return self.model(x)
```

The important change from the univariate implementation is:

```python
nn.Linear(
    window_size * feature_size,
    hidden_size
)
```

instead of:

```python
nn.Linear(
    window_size,
    hidden_size
)
```

The `forward()` method can remain essentially the same because the input is flattened before being passed to the fully connected layers.


# 3. RNN

## 3.1. Difference from the Univariate RNN

For a recurrent model, the input is represented as:

$$
(batch\_{size},\ sequence\_{length},\ feature\_{size})
$$

The univariate input was:

```text
(batch_size, 60, 1)
```

The multivariate input is:

```text
(batch_size, 60, 4)
```

Therefore, the main change is the `input_size` of the RNN.

In the univariate model:

```python
input_size=1
```

In the multivariate model:

```python
input_size=feature_size
```

where:

```python
feature_size = 4
```

### Multivariate RNN

```python
class RNNModel(nn.Module):

    def __init__(
        self,
        feature_size=4,
        hidden_size=128,
        num_layers=1,
        horizon=3
    ):
        super().__init__()

        self.rnn = nn.RNN(
            input_size=feature_size,
            hidden_size=hidden_size,
            num_layers=num_layers,
            batch_first=True
        )

        self.fc = nn.Linear(
            hidden_size,
            horizon
        )

    def forward(self, x):

        output, _ = self.rnn(x)

        # Select the last time step
        output = output[:, -1, :]

        output = self.fc(output)

        return output
```

The RNN architecture itself does not need to be redesigned. The important change is:

```python
input_size=feature_size
```

instead of:

```python
input_size=1
```

The input shape is already correct:

```text
(batch_size, 60, 4)
```

Therefore, unlike the univariate case, **no additional reshape is required**.

# 4. LSTM

The same principle applies to LSTM.

In the univariate case, the LSTM received:

```text
(batch_size, 60, 1)
```

In the multivariate case:

```text
(batch_size, 60, 4)
```

Therefore, the LSTM's input feature size changes from 1 to 4.

### Multivariate LSTM

class LSTMModel(nn.Module):

The main change is:

```python
input_size=feature_size
```

The following parts remain unchanged:

```python
hidden_size=128
num_layers=1
batch_first=True
```

The fully connected layer also remains conceptually unchanged:

```python
nn.Linear(
    hidden_size,
    horizon
)
```

# 6. Conv1D

Conv1D requires a slightly different modification.

In the univariate case, the input might have the shape:

```text
(batch_size, 60, 1)
```

For PyTorch's `Conv1d`, we need:

```text
(batch_size, channels, sequence_length)
```

Therefore, in the univariate case:

```text
(batch_size, 60, 1)
        ↓
(batch_size, 1, 60)
```

For multivariate data:

```text
(batch_size, 60, 4)
        ↓
(batch_size, 4, 60)
```

The four features become the four input channels.

### Multivariate Conv1D

```python
class Conv1DModel(nn.Module):

    def __init__(
        self,
        feature_size=4,
        hidden_size=128,
        horizon=3
    ):
        super().__init__()

        self.conv = nn.Conv1d(
            in_channels=feature_size,
            out_channels=hidden_size,
            kernel_size=3
        )

        self.relu = nn.ReLU()

        self.pool = nn.AdaptiveAvgPool1d(1)

        self.fc = nn.Linear(
            hidden_size,
            horizon
        )

    def forward(self, x):

        # Change:
        # (batch, sequence, features)
        # to
        # (batch, features, sequence)

        x = x.permute(0, 2, 1)
        x = self.conv(x)
        x = self.relu(x)
        x = self.pool(x)
        x = x.squeeze(-1)
        x = self.fc(x)

        return x
```

The main change is:

```python
in_channels=feature_size
```

instead of:

```python
in_channels=1
```

The following operation is still required:

```python
x = x.permute(0, 2, 1)
```

because PyTorch Conv1D expects the feature dimension to be the channel dimension.

# 7. N-BEATS

N-BEATS requires a similar modification to the FFNN because our simple implementation uses fully connected layers.

In the univariate case:

$$
input\_{size} = window\_{size}
$$

For example:

$$
input\_{size}=60
$$

In the multivariate case:

$$
input\_{size} =window\_{size} \times feature\_{size}
$$

Therefore:

$$
input\_{size}=60\times4=240
$$

The input is flattened:

```text
(batch_size, 60, 4)
        ↓
(batch_size, 240)
```

### N-BEATS Block

```python
class NBeatsBlock(nn.Module):

    def __init__(
        self,
        input_size,
        hidden_size,
        horizon
    ):
        super().__init__()

        self.fc_stack = nn.Sequential(

            nn.Linear(
                input_size,
                hidden_size
            ),

            nn.ReLU(),

            nn.Linear(
                hidden_size,
                hidden_size
            ),

            nn.ReLU(),

            nn.Linear(
                hidden_size,
                hidden_size
            ),

            nn.ReLU(),

            nn.Linear(
                hidden_size,
                hidden_size
            ),

            nn.ReLU()
        )

        self.backcast = nn.Linear(
            hidden_size,
            input_size
        )

        self.forecast = nn.Linear(
            hidden_size,
            horizon
        )

    def forward(self, x):

        output = self.fc_stack(x)
        backcast = self.backcast(output)
        forecast = self.forecast(output)
        return backcast, forecast
```

### N-BEATS Model

```python
class NBeatsModel(nn.Module):

    def __init__(
        self,
        window_size=60,
        feature_size=4,
        hidden_size=128,
        horizon=3,
        num_blocks=3
    ):
        super().__init__()

        input_size = (
            window_size * feature_size
        )

        self.blocks = nn.ModuleList([

            NBeatsBlock(
                input_size=input_size,
                hidden_size=hidden_size,
                horizon=horizon
            )

            for _ in range(num_blocks)
        ])

    def forward(self, x):

        # Flatten time and feature dimensions
        x = x.reshape(
            x.size(0),
            -1
        )

        residual = x

        forecasts = []

        for block in self.blocks:

            backcast, forecast = block(
                residual
            )

            forecasts.append(forecast)

            residual = residual - backcast

        output = torch.stack(
            forecasts,
            dim=0
        ).sum(dim=0)

        return output
```

The important modification is:

```python
input_size = window_size * feature_size
```

instead of simply:

```python
input_size = window_size
```

The flattening operation remains unchanged.


# 8. Summary of Changes

The most important differences between the univariate and multivariate implementations can be summarized as follows.

| Model       | Univariate input         | Multivariate input        | Main change                  |
| ----------- | ------------------------ | ------------------------- | ---------------------------- |
| **FFNN**    | `(B, 60, 1)` → `(B, 60)` | `(B, 60, 4)` → `(B, 240)` | `window_size × feature_size` |
| **RNN**     | `(B, 60, 1)`             | `(B, 60, 4)`              | `input_size=feature_size`    |
| **LSTM**    | `(B, 60, 1)`             | `(B, 60, 4)`              | `input_size=feature_size`    |
| **GRU**     | `(B, 60, 1)`             | `(B, 60, 4)`              | `input_size=feature_size`    |
| **Conv1D**  | `(B, 1, 60)`             | `(B, 4, 60)`              | `in_channels=feature_size`   |
| **N-BEATS** | `(B, 60)`                | `(B, 240)`                | `window_size × feature_size` |

Here, (B) represents the batch size.



# 9. What Remains Unchanged?

An important advantage of the multivariate setup is that **most of the training procedure does not need to change**.

The following can remain the same:

### Loss function

```python
criterion = nn.L1Loss()
```

### Optimizer

```python
optimizer = torch.optim.Adam(
    model.parameters(),
    lr=0.0001
)
```

### Batch size

```python
batch_size = 128
```

### Training loop

The same `train_model()` function can be used for all models because all models receive the same batches and produce the same target shape.

### Output layer

All models predict:

```text
(batch_size, horizon)
```

For `horizon=3`:

```text
(batch_size, 3)
```

Therefore, the output layer remains:

```python
nn.Linear(
    hidden_size,
    horizon
)
```

for the models that use `hidden_size` as their final representation.

In addition, the **plotting function, evaluation function, and function for predicting the next Bitcoin** prices can remain essentially the same as those developed in the univariate section. These functions can be reused because the models still produce forecasts for the target variable, Price, with the same forecast horizon.

The main difference is related to **data normalization**. In the multivariate section, we applied Min-Max normalization to the four input features using a scaler fitted on the training data. Consequently, the models learn to predict the normalized Price values, rather than the original Bitcoin prices. **Before interpreting the predicted values in the original price scale, we must apply an inverse transformation to convert the normalized predictions back to their original values.** So in the `predict_next_price` function we add the following codes:

```python
  # Inverse transform the Price
  price_min = scaler.data_min_[0]
  price_max = scaler.data_max_[0]

  prediction = (prediction * (price_max - price_min) + price_min)
```

The central idea is therefore simple:

> **The training procedure remains almost unchanged. The main modifications occur in the way each model receives the four features at every time step.**

For RNN, LSTM, and GRU, the input remains in the form `(batch, sequence, features)`. For Conv1D, the feature dimension becomes the channel dimension. For FFNN and N-BEATS, the time and feature dimensions are flattened, changing the input size from `window_size` to `window_size × feature_size`.
